### Recommendations (inputs; the backlog's decisions override)
- Use SDK runtime discovery as the primary source. Add `claudeModels()` next to claudeAccount() in claude-engine.ts using the same never-yielding streaming query, call `q.initializationResult()` once (its `models` and `account` come from one handshake), close the query, and serve the result from a cached GET /api/runtimes/claude (5 min, ?refresh=1), alongside or merged with /api/claude-account. — supportedModels() and ModelInfo.supportedEffortLevels already describe exactly what this login and org can run, including availableModels narrowing (sdk.d.ts:1427-1467, :3082, :9734). The no-usage pattern and cache already exist (claude-engine.ts:46-61, agents.ts:526/619-623). Reusing one CLI start (~6 s) for both answers avoids a second spawn.
- Add a small versioned registry only as a gap-filler and offline fallback. Put it in packages/shared (e.g. `RUNTIME_REGISTRY = { version: '2026-10-28', sources: [doc URLs], claude: { [modelId]: { label, efforts: EffortLevel[], defaultEffort, prices: [in, out, cacheRead] } } }`). Use it when discovery fails or ModelInfo omits supportsEffort or supportedEffortLevels, and label the UI 'from registry vX' in that case. — packages/shared is already imported by web and server and holds API contract types (ClaudeAccount at shared/src/index.ts:71-81). The ModelInfo capability fields are optional, which is the 'discovery incomplete' case the spec names. Per-model prices in the same table also fix the family-price under-read (claude-engine.ts:153). Skip a Codex section until a Codex engine exists.
- Validate every (runtime, model, effort) triple on the server before queuing a run, in runs.start or the deploy and conversation routes. Look the model up in the discovered list, falling back to the registry. Reject with a 4xx naming the reason (unknown model, model not on this login, effort not in supportedEffortLevels, model has no effort, runtime not connected). Never set Options.fallbackModel. — The CLI silently downgrades unsupported efforts (sdk.d.ts:3014-3018; Claude Code docs 'falls back to the highest supported level'), and fallbackModel silently switches models (sdk.d.ts:1717-1722). Backend validation is the only way to meet the spec's 'no silent substitution' rule.
- Thread the choice through as `RunInput.model` and `RunInput.effort`. In claude-engine.ts use `input.model ?? opts.model ?? agentModel()` and pass `effort: input.effort`, always explicitly, because defaults differ between the API and Claude Code. Add `model TEXT` and `effort TEXT` to agent_runs in one migration, and save the requested values at start. — RunInput is the existing seam (engine.ts:6-27). Reflection inherits via `...input` (runs.ts:354). Retry (runs.ts:369) needs the stored values. Explicit effort avoids the Sonnet 5.5 default mismatch (API says high, Claude Code says medium).
- Persist what actually ran. Record SDKSystemMessage(init).model and the result's modelUsage keys on the run (e.g. `actual_model`), and flag any run where the actual model differs from the requested one. — This meets the spec's 'persist actual model used for each run'. The init `effort` field is documented only for Remote Control frames (sdk.d.ts:6252), so the requested effort that passed validation is the record of effort.
- Do not expose a thinking on/off control. Expose effort only, as the levels the selected model supports. — SDK ThinkingConfig has no 'between_tools' (grep count 0), 'disabled' is a 400 on Opus 5.5 and Sonnet 5.5, and the effort docs say effort is the recommended depth control where adaptive thinking exists.
- Make the demo engine an explicit runtime choice ('Demo, free') instead of letting defaultEngine silently route unconnected stores to FakeEngine. Update the model_not_found message, which still says to set FRONTLINE_AGENT_MODEL. — engine.ts:37-41 swaps the provider without telling the user, which conflicts with 'never silently substitute provider'. claude-engine.ts:36 points at an env var that a per-run picker supersedes.
- Run a one-off probe on this machine before building the picker, with the owner's permission since it starts the CLI: print `(await q.initializationResult()).models` from a no-prompt streaming query. — I did not run it because the task is read-only and starting the CLI may write state under ~/.claude. What supportedModels() returns on this login (aliases or ids, effort fields filled or not) is therefore unverified and decides how much the registry has to cover.

### Recommendations the checker rejected or corrected
- Rec 1: build claudeModels() with 'the same never-yielding streaming query' as claudeAccount and serve it from a new GET /api/runtimes/claude. → claudeAccount's query omits settingSources, so it loads the owner's user, project and local settings (sdk.d.ts:2312-2313). Adding `models` to the existing ClaudeAccount response and route reuses the cache, the ?refresh=1 and the demo short-circuit (routes/agents.ts:526, :619-623) and removes a separate route.
- Rec 3: server-side validation is 'the only way to meet no silent substitution'. → This overstates it. Org effort caps (Enterprise per-role caps or the managed `maxEffortLevel`, sdk.d.ts:9299-9301) clamp `--effort` silently. Nothing documents that ModelInfo.supportedEffortLevels reflects those caps. Validation reduces substitution but cannot rule it out. It must be paired with reading back the applied effort, which is possible via hook input `effort.level` (see missed facts).
- Rec 5: flag any run where the modelUsage keys differ from the requested model, and treat the requested effort as the only record of effort. → modelUsage covers the main loop, Task subagents, sidechains and internal calls such as compaction (sdk.d.ts:5950), so extra keys are expected and the flag would fire falsely. Runtime behaviour under settingSources: [] is unverified.
- Rec 4 rationale: model and effort columns are needed because retry (runs.ts:369) re-calls start() without them. → The rationale is incomplete, and following it as written would drop the values on normal runs. start() only INSERTs a row (runs.ts:103-105). The executor rebuilds RunInput from the DB row (runs.ts:244-264), so every queued run needs the stored columns, not just retries. Three related changes are also needed: start()'s options bag must take them, the queued-duplicate check at runs.ts:92-101 must compare model and effort or two deploys with different models get merged, and a resumed follow-up (runs.ts:75-81) should inherit the previous run's model and effort unless changed explicitly.
- Risk: 'Fable may bill usage credits ... the Deploy dialog should surface that rather than fail mid-run.' → This misreads the failure mode. The routing is not invisible today: engineInfo exposes provider 'demo' per agent, and the UI labels it (AgentDetail.tsx:84 'Demo engine', DeployWizard.tsx:30 'Free demo engine'). The routing is also a deliberate cost guard (engine.ts:32-35). Showing Demo as a labeled runtime in the picker is enough. Letting a Claude runtime be chosen for a demo store would spend usage on fake data and needs an explicit decision, not a quiet routing change.

### Risks
- The CLI silently downgrades unsupported effort ('max' runs as 'high'; levels are clamped to org limits). Without backend validation the picker could show a level that never ran (sdk.d.ts:3014-3018).
- ModelInfo `value` may be an alias such as 'sonnet' or 'opus' that resolves differently per provider and release (sdk.d.ts:1433; model-config docs). Persist resolvedModel or the init `model`, not the alias, or history will drift when aliases move.
- Effort defaults differ between the API docs and Claude Code docs (Sonnet 5.5: high versus medium). Omitting effort makes a run's effort depend on the bundled CLI version.
- Live cost estimates use family prices (claude-engine.ts:153). Exposing legacy models such as Haiku 4.5 or Sonnet 4.6 under-counts cancelled or crashed runs against store budgets by up to about 10x until per-model prices exist.
- Discovery costs a CLI spawn (~6 s, claude-engine.ts:43) and can time out. The Deploy dialog needs a cached or registry fallback state, not a spinner that blocks deploy.
- Resuming a session on a different model is unverified for preserved thinking: thinking blocks are bound to the producing model (claude-api skill). Changing the model on an existing conversation should start a new session or an explicit handoff, as the spec says.
- Fable may bill usage credits on subscription plans (model-config docs). The Deploy dialog should surface that rather than fail mid-run.
- The working tree is mid-cleanup (gamification removal, migration 49 in db.ts:828-832). A new migration for model and effort columns must be numbered after it and coordinated with that session.

### Risks
- The app-server is officially marked experimental, and even the SDK's exec flag is a hidden `--experimental-json`. Codex releases weekly (0.163, 0.164 and 0.165 within days), so the protocol can drift. If the SDK targets the user's installed CLI through `codexPathOverride`, the SDK and CLI versions can differ: SDK 0.165.0 against CLI 0.163.0 here.
- In the read-only sandbox, a Codex agent with the shell enabled can probably still read the owner's files, including the repo and `~/.codex`. The docs do not settle this (unverified), so v1 must turn off `features.shell_tool`.

- If the shared `~/.codex` is used, the owner's personal AGENTS.md, hooks, plugins, MCP servers (Neon, Playwright) and computer-use notify leak into store agents, and agent threads show up in the owner's personal Codex history.
- Store agents expect token streaming, but Codex runs through the SDK show the answer only at the end. Stop kills the process rather than ending the turn cleanly.
- Without dollar costs, the per-store dollar budget (default $5/day) cannot limit Codex runs on a ChatGPT login, and usage counts against the owner's plan limits.

- Each Codex run starts a 341 MB native process, so the memory cost of 3 concurrent runs on Windows is unverified.
- The model and effort catalog differs by account and CLI version (bundled vs remote, default efforts differ), so any static registry goes stale.
- Whether `codex exec` honors MCP servers supplied through `-c mcp_servers.frontline.url=...` overrides is not documented for MCP specifically, only the generic `-c` mechanism. This needs a spike to confirm (unverified).
- The working tree has uncommitted gamification edits from another session (db.ts migration 49, agents-gamification.ts renamed to agents-outcomes.ts). CodexEngine schema work must wait for that or rebase onto it.

### Risks
- If cross-store requests are not checked, store-first conversations with deep links (?run=) or stale ids can show, cancel or approve another store's run, and the backend will not refuse.
- Automatic capture in a workspace with review off would turn agent output into active cards that other agents then retrieve, a loop where unverified claims reinforce themselves. Chat captures need to stay 'proposed' whatever the workspace setting.
- sameCard's 60% word-overlap threshold can merge distinct findings or miss paraphrases. Auto-capture would multiply both errors and flood the Unreviewed queue unless there is a per-run cap.
- Cards saved from chat on a demo store are deleted when that store goes live (kb.ts:89-97). The UI needs to say so, or users will think saved findings were lost.
- Asking the KB with ws=all puts other stores' cards into the paying store's Market Analyst run and session (agents.ts:588-598; ask.ts:48-50). This conflicts with the spec's rule that each conversation keeps one immutable store, unless such conversations are labelled cross-store or kept out of the store's history.
- Card content reaches the prompt as owner-accepted text with no untrusted marker. A malicious page summarised into an accepted card could steer later runs. The only defences today are review (on by default) and the SQUAD_RULES sentence.
- Error logging records full stacks and third-party error text without checking them (app.ts:80; agents.ts:281). No credential leak was found, but there is no test that proves none can happen.
